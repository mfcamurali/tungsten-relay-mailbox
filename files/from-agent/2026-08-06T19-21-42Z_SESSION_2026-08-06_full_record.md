## Every real bug found and fixed tonight (not cosmetic — each has a concrete failure scenario)

1. **Retry-engine + calibration-verdict logging invisible in real time** (WARRANT#120/121/125). The entire PRI retry engine (all 5 phases), the diagnosis summary, the Phase 6 PRI-result path, and the full `CALIBRATION RESULT | STAND DOWN` verdict report — including the single most important line in the whole system — used `Print`/`PrintFormat` exclusively (969 of 1,067 total logging calls file-wide), invisible to the one channel (`TUNGSTEN_live.log`) this project's own tooling treats as real-time-reliable. This is what caused the "is it frozen" scares. Converted every one of these call sites to `TLog`. Zero decision logic touched — purely a logging-channel swap.

2. **`signalPF` bracket mismatch, Phase 2 regime intelligence** (WARRANT#123, line ~5077). The win/loss determination for a bar used regime-specific TP/SL approximations (2.0/1.2 for reversals, 1.5/1.0 for range/volatile, 1.8/1.2 for pullback, etc.), but the profit/loss *magnitude* recorded for that same outcome always used a flat 2.5/1.5 — correct only for trend regimes (0/1), wrong for every other regime. This fed a systematically wrong ratio into `g_RegimeCorrelations[].signalPF`. Fixed by using the same regime-specific values already computed for the win/loss test.

3. **17 duplicated-literal TP/SL-bracket sites file-wide** (WARRANT#122/123/126) — the exact "diagnostic default bracket" (2.5x ATR TP / 1.5x ATR SL) hardcoded independently across Phase 1 baseline/sensitivity/refinement loops, P3B's core outcome precompute, an isolation-seed eval, PASS13's feature diagnostic, a volatility-tercile holdout check, and 2 direct-assignment sites a parallel audit agent found that the first sweep's grep pattern (multiplication only) missed. Consolidated onto the existing named constants `P3B_DIAG_BRACKET_TP_ATR`/`_SL_ATR`. Zero behavior change — same literal values, now named once instead of duplicated ~19 times.

4. **`recentWinRate` denominator bug** (WARRANT#124, line ~24873) — the field `CalculateKellyCeiling()` reads directly to set its live edge input was computed as `wins / 20.0 * 100.0`, a HARDCODED denominator, even though the loop just above it correctly computes `_total_rb20282 = MathMin(g_State.totalTrades, 20)` (the real sample count) and only iterates that many real results. Every live deployment's first ~20 trades — the entire warm-up window, exactly when accurate sizing/gating matters most — had a systematically understated win rate (e.g. 5/5 real wins would compute as 25%, not 100%). Fixed to use the real sample count. Can only increase the reported rate during warm-up, never decrease it below the old behavior once 20+ trades exist.

5. **Hard risk floor gap, `ExecuteRangeTradeIfValid()`** (WARRANT#127, line ~32527) — a live order-placement path (range trading) computed its own independent risk-multiplier stack and never routed through `OptimizePrecisionLotSize`, so it never inherited WARRANT#109's hard 7.5%-per-trade ceiling. Not exploitable today (worst case under present constants: 2.75%), but `g_RangeRiskPercent` is a plain tunable global, not a compile-time constant — nothing stopped a future parameter change from silently exceeding the ceiling on this one path while every other risk calculation stayed protected. Added the same reduce-only floor check used elsewhere. Currently a no-op; only ever prevents a *future* silent breach.

## Real findings surfaced but deliberately NOT force-fixed (and why)

- **`g_RegimeStats[].avgR`** is a genuinely dead field (written once to 0.0 at init, never updated, never read anywhere) — but its structural twin `g_SessionStats[].avgR` IS correctly maintained live, strongly suggesting an unfinished parallel build. Not a one-line fix: the struct doesn't even track a `totalR` accumulator per regime yet, and wiring it needs a design decision about what should consume a per-regime average-R (regime-quality scoring is the obvious candidate, unspecified). A naive Bonferroni/Šidák correction using the raw draw count would be statistically WRONG for a correlated continuous search space (over-conservative to the point of breaking the gate). The statistically appropriate tool — the real Bailey-López de Prado PBO-CSCV statistic — was already shipped in a prior session (WARRANT#62/98) and confirmed firing correctly live tonight (`PBO-CSCV 0.771 > 0.50 → regularized`). Reported honestly as substantially already solved rather than bolting on a redundant, wrong-shaped fix.
