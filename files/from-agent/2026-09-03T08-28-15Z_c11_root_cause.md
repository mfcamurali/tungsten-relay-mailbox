# C1.1 — ROOT CAUSE OF THE SCORE-FUNCTION DIVERGENCE

**WARRANT#381 · 2026-09-03 · build TUNGSTEN_10.66_APEX_QUANT_SLS(181).mq4 · ANALYSIS, no terminal**

Instruments: `research_layer/c11_gap_attribution.py` (11 self-tests), outputs
`c11_mutation_map.json` and `c11_gap_attribution_result.json`. Read-only: the `.mq4` was not
edited, no executable was launched.

---

## 0. THE HEADLINE, IN ONE PARAGRAPH

The standing account of C1.1 is that the live scorer applies dozens of mutations its
explicit-weight twin does not, and that closing the gap means reconciling those mutations. That
account is **the second cause, not the first**. `CalculateEnhancedUnifiedScore` (CEUS) ends with a
terminal rescale — `_norm = totalScore * (88.0 / _refMax)` — that
`CalculateScoreWithWeights` (CSW) has no counterpart for. At the weights in force when the
equivalence test runs, that factor is **88/169 = 0.5207**. Two functions that agreed on every
single term would still disagree by 47.9% of the score. Measured on 50,000 exported bars:
teaching the twin every mutation and leaving the rescale alone moves the mean gap from **18.4 to
19.0 — it gets worse**. Teaching the twin the rescale alone moves it to **4.3, a 77% reduction**.
And the rescale, not any mutation, is the mechanism behind the build's own portal-audit finding
that calibration qualifies 132 of 500 bars and live qualifies 1 — an audit which has been printing
the rescale factor itself, as `mean |enhanced|/|linear| 0.616`, on the same log line, for a month.

## 1. THE COUNT — the "54 mutations" figure is wrong; here is the real accounting

Derived by parsing the shipped source, not by recollection. CEUS spans lines **18279–19156**
(878 lines); CSW spans **7358–7522** (165 lines). Both accumulate into a local named `totalScore`.

| | count |
|---|---|
| assignments to `totalScore` in CEUS | **53** |
| of which: the initialiser `double totalScore = 0.0;` | 1 |
| of which: component accumulations | 6 |
| of which: the synergy bonus (present in both functions) | 1 |
| **MUTATIONS — writes with no counterpart in the twin** | **45** |
| terminal statements after the last `totalScore` write | 5 (3 transform the score, 2 build its reference) |
| **total transformations CEUS applies that CSW does not** | **50** |
| assignments to `totalScore` in CSW | 10 |
| **twin-only writes CEUS lacks** | **2** |

**45, not 54.** By kind: 33 additive, 6 multiplicative, 4 clamps, 2 whole-score replacements
(`GetPatternAdjustedScore`, `ApplyProbabilityIntelligence`). If you group mutually-exclusive
`if/else-if/else` chains into single decision sites the figure is 35 sites; if you count only
statements that change the number the figure is 45; neither reading produces 54. The full
per-mutation enumeration — source line, operator, kind, gate chain, globals read, hard-coded
constants — is in `c11_mutation_map.json`.

**Three things the "54 mutations" framing hid, all of which change the answer:**

1. **The largest divergence is not a mutation at all.** Lines 19145–19153 never touch
   `totalScore`; they build `_refMax`, divide by it into `_norm`, apply a soft knee at 92, and
   clamp into `g_LastBlendedScore`. Any enumeration that scans for writes to the accumulator —
   the obvious way to count mutations — stops three lines short of the biggest one.

2. **The divergence is bidirectional.** CSW has two writes CEUS lacks: the type-aware quality
   multiplier `totalScore *= _qualMult` (0.85–1.10, line 7515) and its own ±100 clamp (7518). Any
   plan that only teaches the twin what the live scorer does leaves these behind.

3. **One component is not shared, and the parity test cannot see it.** CEUS's pattern term comes
   from live micro-pattern state (`10.0 * microConfidence`) or, failing that, `PATTERN233_Score`.
   CSW's comes from `DetectMicroPatternAt(bar).confidence * 10.0`. Three formulas, two functions,
   one component. `TUNGSTEN_score_parity.csv` has columns `mtf_mismatch`, `momentum_mismatch`,
   `volatility_mismatch`, `volume_mismatch`, `session_mismatch` — **and none for pattern**.
   `check_c13_parity.py` reports it SHARED because the live scorer calls `PATTERN233_Score`
   *somewhere* in its body, and prints a note calling the difference a "live-only overlay". Read
   in the source it is not an overlay: it is an `if/else` that *replaces* the shared formula. The
   two paths' pattern terms have never been numerically compared on any run.

## 2. THE INSTRUMENT MEASURES A FLOOR — 34 of the 45 mutations cannot fire in it

`RunScoreParityTest` has exactly one call site: line 34242, inside `OnInit`, immediately after the
historical export and before calibration begins. Re-derived from the source on every run of the
harness:

- OnInit contains **no** call to `LoadSystemState()` — no saved calibration is restored.
- OnInit sets `g_Calibration.isCalibrating = false` and sets **none** of `g_WeightsOptimized`,
  `g_ICMeasured`, `g_CorrelationsLearned`, `g_IndIntelReady` to true.
- The test samples bars at `30 + i*stride`, i.e. always `shift > 0`.

So at the moment the ~21-point gap is measured:

| gate class | mutations | can fire? |
|---|---|---|
| gated `shift == 0` (all of Layers 9–14, score velocity, convergence bonus) | 22 | **no** |
| needs `g_WeightsOptimized` / `g_CorrelationsLearned` / `g_IndIntelReady` / `g_ProbDB.calibrated` (CCA, indicator confluence, probability intelligence, market memory) | 4 | **no** |
| needs live market-state globals still zero at OnInit (`intelligence.vwap`, `marketStructure.valueArea*`, `g_PatternState.pattern*Signal`) | 8 | **no** |
| unconditional or gated only on `!isCalibrating` | 11 | **yes** |

**34 of 45 are switched off in the measurement.** Corroborated independently by the data: the
export's `comp_pattern` column takes only the values {0, ±3, ±5} across all 50,000 bars, which is
exactly `PATTERN233_Score`'s range — the live micro-pattern branch never fired, as the state model
predicts.

Consequence: **the reported 21.42 is a floor, not the live divergence.** With calibrated weights,
at `shift == 0`, with every intelligence layer live, the true gap is larger and has never been
measured. This does not weaken the finding below — it means the thing that needs fixing is bigger
than the number on the artefact.

Also worth recording as an instrument gap, not a verdict change: `check_authority_criteria.py`'s
family enumeration misses `CalculateUnifiedScoreCoreAtBar` (line 49937), a **fourth** family
member with 12 call sites. It is a genuine wrapper — it installs candidate weights, calls CEUS,
restores — but the checker's wrapper rule requires the literal `return <member>(`, and this one
assigns to `_score` and returns the variable. C1.1's verdict is unchanged (wrappers are allowed);
what changes is that a material share of calibration already scores through the live engine.

## 3. THE ATTRIBUTION — measured, not asserted

### 3.1 How the mutation payload is recovered

`RunHistoricalScoreExport` runs from the same OnInit, in the same cold state, and writes per bar
both CEUS's final score and CEUS's own six captured pre-weight components. Its scorer,
`CalculateUnifiedScoreCoreAtBar`, calls CEUS. With `g_WeightsOptimized` false every weight is
1.0, so the six components sum to exactly the quantity CSW composes. That makes the total
mutation payload recoverable per bar:

```
score  = K · (base + M)          K = 88 / _refMax,  base = Σ comp_*
  ⇒  M = score / K − base
```

### 3.2 K is identified from the data, not assumed

`_refMax = 42·w_mtf + 25·w_mom + 18·w_vol + 14·w_volu + 10·w_ses + 22·w_pat + 20 + 18`. At unit
weights that is 169, so K = 0.5207. **This is not taken on trust.** If K is right *and* the
sequential-quality multiplier really is one of {0.82, 1.00, 1.10, 1.25}, then every bar on which
no additive mutation fired must land on exactly one of four `score/base` ratios. Of 41,369
eligible bars, **2,667 (6.45%) land inside a 0.0012-wide window around one of the four**, against
0.96% expected from a smooth density — a **6.7× enrichment**, with all four predicted values
individually visible as spikes. The build's own WARRANT#278 comment independently records the
same constant ("pinned every strong bar to 52.07"): 100 × 88/169 = 52.07.

### 3.3 The counterfactuals — mean |gap| over 49,999 bars, in the points the test reports

| scenario | twin returns | mean \|gap\| | vs shipped |
|---|---|---|---|
| **as shipped** | `clamp(base)` | **18.36** | — |
| **(a) twin also applies all 45 mutations** | `clamp(base+M)` | **18.99** | **+0.63 — worse** |
| **(b) twin also applies the terminal rescale** | `clamp(K·base)` | **4.31** | **−14.06 (−77%)** |
| **(a+b) twin applies both** | `clamp(K·(base+M))` | **0.00** | identity |

Supporting quantities: mean \|base\| 38.97 · mean \|CEUS score\| 20.90 · mean \|M\| 8.28 (max 68.8)
· rescale term mean \|(1−K)·base\| **18.68** · mutation term mean \|K·M\| **4.31**.

**Why (a) makes it worse, which is the load-bearing part.** The mean signed mutation payload in
the signal direction is **+0.94** — the mutations push *with* the signal, while the rescale
shrinks it. They were partially cancelling. Add the mutations to the twin without the rescale and
you remove the cancellation, so the gap widens. This is the specific claim that falsifies the
"reconcile the mutations" plan.

### 3.4 Model validation against what the build itself measured

Seven equivalence runs on this build report mean \|diff\| of 19.63–22.62 (mean of run means
**21.05**), all FAIL. The model above reproduces **18.36** — **87% of the measured value** — on a
different bar population (50,000 exported vs ~200 sampled) and with the unshared pattern component
left inside the residual. Every implied per-bar payload M falls inside the band the source's own
hard-coded coefficients and clamps permit (0 violations in 49,999 bars).

### 3.5 What is NOT established — stated rather than glossed

- **The decomposition holds at unit weights**, the configuration the equivalence test runs in. K
  depends on the calibrated weights; the production factor is a different number and is not
  measured here. It is bounded: `_refMax` has a floor of 60 (K ≤ 1.467) and no ceiling, so under
  calibrated weights K can be either larger or smaller than 0.5207. **This should be measured
  before any fix is sized.**
- **CSW is modelled as `clamp(Σ CEUS components)`.** Exact for five of six components (the parity
  test measures 0 mismatches on all five, sign-exact for MTF and momentum). Not exact for pattern
  — a per-bar difference of up to 15 points that sits inside the 13% residual.
- **M is a total.** No split of M across individual mutations is claimed. The export carries no
  per-mutation column, and inventing one would be exactly the failure this campaign exists to
  refuse. The only decomposition supported is the regression of M on base: slope **0.0762**,
  correlation **0.300**, which puts roughly **3.0 of the 8.3** mean payload on the multiplicative
  mutations (`_seqMult`, the value-area 0.92 damp) and the remainder on the additive ones. Within
  the additive group the export cannot rank PPS against BB against ATR-momentum, and this document
  does not.

## 4. WHY THIS IS NOT A TIDINESS CRITERION

Calibration fits `g_RegimeOptimalThresholds` by counting bars where `|CSW|` clears a candidate
threshold. Live applies that same signed number to CEUS's output through the `50 + signed/2`
bridge (7+ sites). CEUS's output is the twin's roughly halved. Same 50,000 bars, same threshold:

| signed threshold | \|twin\| qualifies | \|live\| qualifies | ratio |
|---|---|---|---|
| 30 | 62.25% | 24.52% | 3× |
| 40 | 45.97% | 8.88% | 5× |
| 50 | 32.35% | 2.55% | 13× |
| 55 | 26.54% | 1.29% | **21×** |
| 60 | 20.75% | 0.63% | 33× |

The build's own portal audit reports **132 of 500** bars qualifying on the calibration scorer and
**1 of 500** on the live scorer. Twin-scale reaches 26.4% at signed threshold 55.0; at that same
threshold the live scale qualifies 1.29% — **6 of 500**. The 132-vs-1 collapse follows from the
scale factor alone and needs no second cause.

### 4.1 The build has been measuring the rescale factor for a month without naming it

The portal audit (source line 44052, `forge-organism portal-audit`) computes exactly the ratio
this document derives — `MathAbs(_pgEnhanced)/MathAbs(_pgLinear)`, live over twin — and logs it.
Three runs on this build:

```
2026.09.01 00:00:24   mean |enhanced|/|linear| 0.670   linear-qualifies 77   ... 99% fewer
2026.09.02 19:26:02   mean |enhanced|/|linear| 0.616   linear-qualifies 132  ... 99% fewer
2026.09.02 20:31:55   mean |enhanced|/|linear| 0.789   linear-qualifies 158  ... 86% fewer
```

The same quantity computed from the export is **0.565** — the same number, from a different
instrument, on different bars, in a different state. (The portal audit runs *after* calibration,
so its `_refMax` is built from calibrated rather than unit weights and its K is correspondingly
different; that spread, 0.62–0.79, is the first direct evidence of what K becomes in production
and is the reason step 2 of §5 exists.) The audit's own human line reads *"The two scorers
disagree on how many bars qualify"* — true, and the reason is a scalar multiplier printed on the
same line.

Related, and worth recording: WARRANT#276's comment observes that *"the live scorer's |score|
never exceeded 52.1 across 50,000 exported bars while every regime threshold sat at 70"*.
52.1 = 100 × 88/169 = the rescale factor applied to a fully-saturated raw score. The build
diagnosed that ceiling as a threshold-provenance bug (`g_BaseThreshold` never written by Phase 1)
and WARRANT#278 relieved the symptom by raising `SCORE_PRECLAMP_LIMIT` from 100 to 400 — the
current export reaches 96.7. Both readings were correct about what they looked at. Neither
identified the divisor.

This is the mechanism of the self-throttling recorded in the project state as *"Build CANNOT open
a trade — no-edge diagnosis suppresses its own score below its own threshold floor."* C1.1 is not
a coherence nicety upstream of the edge question. **It is a plausible sufficient explanation of
why the edge question has never been askable**, because the system has been searching thresholds
on one scale and trading them on another. That does not prove an edge exists — but it does mean
the four independent no-edge results were produced by a system whose live gate was ~2× tighter
than the gate its search believed it was fitting.

## 5. WHAT C1.1 WOULD ACTUALLY REQUIRE

The criterion accepts two routes: **a single remaining implementation**, or **an equivalence test
showing agreement**. The first is not available without deleting the ability to score a bar under
*candidate* weights, which is the entire purpose of weight search. So the honest target is the
second — and the work is to make the two agree, then let the existing WARRANT#358 test say so.

### Option (a) — teach the twin the mutations

**Measured effect: mean gap 18.36 → 18.99. It does not close the gap; it widens it.**

Half the mutations are structurally impossible in the twin anyway: 22 are `shift == 0` only (the
twin is called on arbitrary historical bars, out of order, by weight search), and the Layer 9–14
inputs come from `CalculateMarketFeatures(0)` — live-bar state the twin cannot have. A faithful
port is not merely large, it is not well-defined.

- **Breaks:** every calibration phase's runtime (the twin is called in inner search loops — 11
  direct sites plus 7 via `...Ex`; adding 45 mutations including several indicator-recomputing
  loops multiplies phase cost); the twin's determinism under out-of-order bar scan.
- **Must be proved first:** that each ported mutation is bar-local. Cannot be proved for the
  `shift == 0` group.
- **Size:** very large, and it is measured to make the criterion's own number worse.
- **Verdict: reject.**

### Option (b) — make the twin apply the same terminal transform ✅

**Measured effect: mean gap 18.36 → 4.31, a 77% reduction. The residual is exactly `K·M`.**

The change is small and localised: CSW's tail becomes the same `_refMax` / `88` divide / soft-knee
/ clamp that CEUS's tail already is, extracted into one shared helper both call. Note this is a
*normalisation*, not a mutation — it is deterministic in the weights and the running total, has no
live-state dependency at all, and is therefore exactly the kind of thing the twin *can* reproduce.

- **What breaks:** every threshold currently stored in `g_RegimeOptimalThresholds`,
  `g_CurrentThreshold`, `g_BaseThreshold` and every `baselineThreshold` / `regimeThr` constant in
  the calibration phases was fitted against the *unnormalised* twin. Rescaling the twin makes all
  of them wrong by ~1.92× **in the direction that makes the system trade more**, so this must not
  ship without recalibration. Every CSW consumer gates on `MathAbs(sc) < threshold` — absolute,
  scale-sensitive, no consumer uses rank alone. The `50 + signed/2` bridge sites are unaffected
  (they consume the signed threshold, not the twin).
- **Must be proved before it ships:** (i) a full recalibration under the flag, with thresholds
  refitted on the new scale; (ii) the WARRANT#358 equivalence test showing the composed-total gap
  falls to the predicted ~4.3 and no further — a *larger* residual means an unmodelled divergence,
  a *smaller* one means something else moved too; (iii) K measured under calibrated weights, not
  assumed to stay 0.5207.
- **Size:** ~25 lines of source, one shared helper, one input flag. Small change, large
  consequence — which is precisely the profile WARRANT#226's pattern exists for.
- **Ship shape (the WARRANT#226 pattern):** an input `bool ScorerIdentityNormalise = false`,
  defaulting OFF exactly as `RunScoreParityTestOnInit` and `ExportHistoricalScoreOutcomes` do; the
  new tail runs only when the flag is on; `RunScoreParityTest` already writes
  `TUNGSTEN_score_equivalence.csv` on every init and needs no change to become the proof. Flag OFF
  must reproduce today's 21.05 exactly, to the digit — that is the "flag-on equals flag-off"
  half, run first, before anyone looks at flag ON.

### Option (c) — declare one authoritative, demote the other to a diagnostic

**Not available as stated, but its useful half is already true.**

Neither can be demoted: CEUS cannot score candidate weights without the
`g_RegimeOptimalWeights` install/restore dance, and CSW cannot reproduce live-bar state. But
`CalculateUnifiedScoreCoreAtBar` already *does* the install/restore and routes to CEUS, and 12
call sites already use it. Migrating the remaining 18 CSW/CSW-Ex sites onto it would leave one
implementation and satisfy C1.1's *first* route outright.

- **Breaks:** calibration runtime, hard. CEUS is 878 lines including several multi-bar indicator
  loops; CSW is 165. Weight search evaluates the twin O(candidates × bars) — the inner loops at
  38310 / 42288 / 48157 / 57429 are exactly the hot path. This is a throughput question, not a
  correctness one, and the 90-minute calibration budget is the constraint.
- **Must be proved first:** that a full calibration still completes inside its budget, measured,
  not estimated.
- **Size:** medium in lines (18 call sites, mechanical), unknown-to-large in run cost.
- **Verdict: the right end state, gated behind (b).** Do (b) first — it is small, it is measured
  to close 77% of the gap, and it makes (c) a pure refactor with no scale change left in it.

### Recommendation

**(b), then (c). Reject (a).**

(b) is the only option measured to reduce the gap, it is ~25 lines, and it is the direct cause of
the qualification collapse in §4. (c) afterwards, gated on a timed calibration. (a) is measured to
make the criterion's own number worse and should not be attempted.

**Ordered next steps, all ANALYSIS or BUILD, none needing a terminal until step 4:**

1. **ANALYSIS.** Add a `pattern_mismatch` column to `RunScoreParityTest` and compare CEUS's
   pattern term against `DetectMicroPatternAt`. This is the one component whose divergence is
   currently invisible, and it is inside the 13% residual. *(One build + one init run.)*
2. **ANALYSIS.** Log `_refMax` and K per scoring pass so the production factor under calibrated
   weights is measured rather than extrapolated from 169. The portal audit already brackets it at
   0.62–0.79 (§4.1); this makes it exact and per-regime. *(One build + one init run.)*
3. **BUILD.** `ScorerIdentityNormalise`, default OFF, shared tail helper. Prove flag-OFF
   reproduces 21.05 to the digit before touching flag ON.
4. **CALIBRATION.** One full run with the flag ON and thresholds refitted, then read
   `TUNGSTEN_score_equivalence.csv`: the composed gap must fall to ~4.3, and the qualification
   rate at the refitted threshold must stop collapsing between the two scorers.
5. **BUILD.** Migrate the 18 remaining twin call sites to `CalculateUnifiedScoreCoreAtBar` if and
   only if step 4's calibration completed inside budget.

**One-sentence honest headline (Rule FF-15):** C1.1 remains NOT MET; the next four steps are two
ANALYSIS runs and one BUILD that need no terminal, and the critical path runs through a ~25-line
change whose effect is already measured on data already held.
