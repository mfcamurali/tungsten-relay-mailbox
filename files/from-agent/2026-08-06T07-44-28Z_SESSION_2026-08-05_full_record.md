## Phase 1 — first live run and the diagnosis that shaped everything after

Launched SLS(95) live (USDJPY M5, XM Global demo). Watched Phase 0 pass, Phase 1 baseline barely
clear random (~30% WR), and all 9 Phase 3B regimes independently find in-sample WR of 44-73% —
every single one then correctly killed by fit-check/resample-check (holdout gaps of -20 to -42pp,
"same-scorer overfit"). Manuel's read, watching live: *"edge should be found, it just swings between
positive and negative a lot."* Investigation confirmed his instinct with real evidence: the
Pre-Flight Phase Table (already-existing machinery) measures statistically significant sign
inversions (t up to 8.86) across session x displacement x volatility cells — real, time-varying
structure — but states outright *"nothing here updates a live weight or trading decision this
pass."* The guardrails were working correctly; the gap was that a single fixed-window linear search
structurally cannot capture non-stationary signal, and the diagnostic proving that already existed
but was never wired forward.

**WARRANT#112**: Found and fixed the mechanistic contributor — Stage 4-CA (one of six weight-search
stages in Phase 3B) used bound `[0.30,2.50]` while five sibling stages agreed on `[0.05,4.0]`,
sandwiched between two wide-bound stages so it silently clamped candidates to a false local optimum.

**WARRANT#113**: Wired the Pre-Flight substrate diagnosis onto every "no edge found" line, so each
null result now states whether the regime looked flat or time-varying — confirmed firing correctly
on the next live run.

## Phase 2 — a real crash, correctly root-caused as my own tooling, not TUNGSTEN

Mid-relaunch, a Monitor task I'd armed to watch the live run went silent for over a minute despite
dense log activity. Diagnosed as PowerShell-through-Bash-pipe buffering, not a wrong log path.
Switched to file-redirected background processes + `tail -f` monitors. Then: stopped the broken
monitor, and `terminal.exe` died moments later with zero trace in Windows System/Application event
logs — no crash, no hang detection. Root-caused (not guessed) as Windows Job Object cascade-kill:
the Monitor-wrapped bash task and the terminal.exe it had spawned shared a process tree, so stopping
the wrapper killed the terminal as a side effect. **Fixed my own approach going forward**: always
launch long-lived processes via fully detached `Start-Process` with output redirected to a real
file, never through a pipe that might later need stopping. Documented this as task #9, resolved by
changed practice rather than a code fix (there was no TUNGSTEN bug here).

Separately root-caused why the pasted MT4 GUI content kept outrunning what I could observe: MT4
batches disk flushes to the Journal log independent of its in-memory GUI rendering — confirmed by
two direct `FileShare.ReadWrite` reads 10 seconds apart returning byte-identical stale content while
the EA's own `TUNGSTEN_live.log` (flushed on every write) showed real progress. Not fixable from
outside the process; explained honestly rather than claimed solved.

## Phase 4 — "memory at every scale... structurally sound"

Systematic write-count-vs-read-count audit of every persisted binary structure in the file.

**WARRANT#116 (CRITICAL)**: `SaveSystemState`/`LoadSystemState` — 110 `FileWriteDouble` matched 110
`FileReadDouble` exactly, but 60 `FileWriteInteger` vs only 59 `FileReadInteger`. Traced call-by-call:
`g_CorrelationsLearned` is written as an integer immediately before the 9-regime correlation-
intelligence loop by BOTH save paths (`SaveSystemState` and `SealArmedSave`), but nothing on the read
side ever consumes it. Because MQL4 file reads are strictly positional with no self-describing
format, this permanently shifted every field read after it — for the REST of that function — by 4
bytes, on every single instant-restart. Root-caused a real cold case: WARRANT#91 (2026-07-23) had
found saved win rates loading as *"595048703%"* and built a sanitize-on-load safety net for the one
row of fields it checked, without ever finding why — that symptom is exactly what a double looks
like read from a 4-byte-misaligned offset. Everything downstream of the gap (avgHurst/avgATRPct/
avgEntropy/avgMomentumBias/avgBodyRatio/avgStructureClarity, Discovery params, ComponentWeights, all
9 regimes' actual calibrated weights) had been silently corrupting on every reload since at least
mid-July. Fixed with the one missing read, in the exact position both writers place it.

Confirmed clean by the same audit technique: Living-Edge cells + armed tail, ProbDB armed tail +
per-pattern, Forge SR-history tail, Forge champion register tail, P3B mid-calibration checkpoint,
comprehensive learning data. Seven pairs checked, one bug, the worst possible kind.

## Phase 5 — relaunch, a second live run, and the events-feed detour

Relaunched SLS(99) (chart swap only, no rebuild needed at that point) to live-test the pending
warrants. Watched Phase 0-3B complete again — same "9/9 no edge" pattern, WARRANT#113's substrate
annotations confirmed firing on every regime line. Manuel flagged the SEG feed staleness warning
that had appeared on every single run all night and had been noted but not yet actually chased down.

**Root-caused and fixed**: `update-tungsten-events.ps1` (the weekly scheduled refresh) hardcoded
`pwsh.exe` at the MSI install path; PowerShell 7 on this machine is installed via the Windows Store
package instead. Confirmed via the script's own error log that every attempt since at least
2026-07-10 hit this check and silently gave up — even though the wrapping Scheduled Task reported
success every week, because it only launched the wrapper, which then failed past where Task
Scheduler could see it. `TUNGSTEN_events.csv` had been stale 17 days as a direct result. Fixed the
resolution to be dynamic (`Get-Command`), then performed the actual refresh directly via WebSearch
(7 verified events, USD + AUD, Aug 6-14) rather than waiting for the next Monday.

**WARRANT#117**: Found the Pre-Flight cost gate reads `g_CalibratedAvgSpread`, a variable set inside
Phase 1 — but Pre-Flight runs before Phase 1, unconditionally, every time. Not an occasional gap: a
structural guarantee that this gate would print "not yet calibrated" forever, confirmed identical on
every Pre-Flight print across all 3 runs watched. Fixed with a live `MarketInfo` spread fallback,
honestly labeled as a live snapshot rather than the calibrated average.

Manuel closed MT4 manually at this point — correctly recognized as intentional, not investigated as
a mystery crash.

**WARRANT#118**: Built real-time synthesis into TUNGSTEN itself per Manuel's request to "automate
most of the work we've had to do." Honest framing: not a new AI layer, but TUNGSTEN performing the
exact aggregation done by hand three times that night — reading each regime's substrate annotation
and reaching one verdict. Added a synthesis line to the all-9-regularized fallback: counts how many
regimes show real measured structure (flip>0 or |t|>3) vs genuine flatness, states the verdict
outright ("MOSTLY TIME-VARYING... not evidence the signal is absent" or "MOSTLY FLAT... a genuinely
weak signal"). Zero new computation, zero effect on any live decision — pure synthesis of
already-computed truth.

## Phase 6 — forge-learn

Manuel asked for a new agent, "forge learn," described in his own words as wanting comprehensive,
trustworthy, self-correcting problem-solving built into every layer — explicitly including the
phrase "no bugs no loopholes no blindspots." Authored `.claude/skills/forge-learn/SKILL.md` honestly:
flagged plainly as *not* a delivered charter document (unlike every other forge-family skill, which
came from files Manuel physically delivered) — this one is Manuel's spoken request translated into a
concrete discipline by the agent. Explicitly rejects "no bugs" as a claimable end-state, reframing
trustworthiness as "every claim backed by a diff-verified fix or an honest clean-audit report,"
because a skill that promised perfection would be lying the moment it was installed. Formalized the
four techniques that had already worked that session (structural pairing audits, cross-stage
consistency audits, infrastructure tracing, real-time synthesis) rather than inventing a fifth.

**Pass 1** (cross-stage consistency): **WARRANT#119** — found two different fallback threshold
floors (50.0 vs 18.0) for the identical "no validated edge" concept in Phase 3B's per-regime loop,
in two sequential (not mutually exclusive) if-blocks, so the lower floor silently overwrote the
higher one whenever `g_BaseThreshold` landed in [18,50) — currently masked because `g_BaseThreshold`
has consistently landed near 70 in every run observed, but a real, mechanically verified bug.
Fixed by making the second check an `else if`.

**Pass 2** (infrastructure tracing) found something larger than TUNGSTEN itself: the identical
hardcoded-`pwsh.exe`-path bug from the events-feed fix also existed in `relay-listener.ps1` — the
script that cold-starts a fresh Claude session whenever a mailbox message arrives with nobody
watching, i.e. the entire mechanism async relay messaging depends on — and in
`install-relay-listener.ps1`, whose own "fallback" path was already stale (version-pinned to
7.6.3.0 against the actually-installed 7.6.4.0). Confirmed via `.listener-error.log` (read correctly
as UTF-16 this time, not raw `cat`) that the listener's version fired repeatedly 2026-07-11 through
07-13 before going silent — not because it was fixed, but because a Claude session has stayed
continuously active since, masking it via the "already running, skip" branch. Fixed both the same
way. Wrote a persistent memory (`pwsh_path_fragility_pattern.md`) recording the general pattern so
it can never be silently reintroduced or rediscovered from scratch by a future session.
