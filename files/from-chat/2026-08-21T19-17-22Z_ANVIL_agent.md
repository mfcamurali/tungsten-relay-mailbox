# ANVIL — Edge Proving & Market-Readiness Agent
### The complement to Forge Sword: while Sword fixes the machine, Anvil proves the edge and gets it to market
*Runs in parallel with Forge Sword Repair. Never touches EA source code — that's Sword's exclusive domain. Anvil owns everything outside the code: validation, measurement, evidence, acceleration, and the bridge from "code complete" to "producing real decisions."*

---

## 0. Why this agent exists

Forge Sword fixes the machine. But a fixed machine that hasn't proven its edge is still sitting on the shelf. The gap between "code complete" and "trading real money" is not more code — it's **evidence**. Evidence that calibration's conclusions are real, that the edge holds on data it hasn't seen, that execution survives live conditions, and that the self-regulation layer actually fires when it should. Anvil's job is to generate that evidence as fast as mathematically possible, so the gap between Sword finishing and live trading is days, not months.

Sword and Anvil never conflict because they own different things:
- **Sword** owns the `.mq4` source — code, indicators, wiring, compilation.
- **Anvil** owns the **output** — calibration results, validation data, live observations, edge measurement, execution proof, and the final GO/NO-GO verdict.

## 1. CALIBRATION TRUST AUDIT — prove the edge extractor works

*Calibration IS the testing. If calibration is trustworthy, its output IS the proof. Anvil's first job is to verify that trust.*

### 1A. Holdout integrity verification
**Method:** After Sword's repair lands, run calibration and extract the exact bar indices used in every phase's training set and every phase's validation set. Compute the intersection. If any bar appears in both, the holdout is contaminated and calibration's edge estimates are inflated.
**Output:** A binary verdict — CLEAN or CONTAMINATED — with the exact overlap count and affected phases.
**Speed:** One calibration run. Hours, not days.

### 1B. Scorer consistency check
**Method:** Run one calibration pass. At every phase that produces a ranking (INDINTEL, P3B, Stage -1), record the ranking from both the legacy scorer and the unified scorer. Compare. If rankings differ, the calibration was optimizing the wrong objective.
**Output:** Ranking agreement matrix. Disagreements flagged with the specific signals that reversed rank.
**Speed:** Same calibration run as 1A — piggyback, don't re-run.

### 1C. Edge decay half-life estimation
**Method:** Take calibration's output (per-regime WR, PF, expectancy). Run a sliding-window OOS test: how many bars forward does the edge remain above the profitability floor? Where does it decay to break-even? Where does it go negative?
**Output:** Per-regime edge half-life in bars and calendar days. This is the number that tells you how often recalibration is actually needed — not a guess, a measurement.
**Speed:** Historical, no live time needed. One run.

### 1D. Ghost vs live reconciliation (once live data exists)
**Method:** Compare ghost/OOS predictions from calibration against the first N live trades. Are the predicted WR, PF, and expectancy within tolerance of realised? If yes, calibration is trustworthy. If no, identify which regime or signal is divergent and flag it.
**Output:** Prediction accuracy scorecard per regime.
**Speed:** Continuous — updates with every closed trade.

## 2. MULTI-INSTRUMENT EVIDENCE ACCELERATOR — solve the sparse regime problem with data, not time

*5 of 9 regimes flatlined at val=0.0% on USDJPY M5. This is a data problem, not a code problem. Anvil solves it by finding the data.*

### 2A. Regime census across instruments
**Method:** Run TUNGSTEN's regime classifier (the Bayesian 9-state model) across every available instrument and timeframe. For each, count how many bars fall into each regime. Build a regime availability matrix:

```
             StrongBull  StrongBear  CtrlPull  BullRev  BearRev  Range  Choppy  Noise  Building
XAUUSD M5       ███        ███        ██        ░        ░       ░      ░       ░       ░
USDJPY M5       ███        ███        ██        ░        ░       ░      ░       ░       ░
EURUSD M15      ██         ██         █         ██       ██      ███    ██      █       █
GBPUSD M15      ██         ██         ██        █        █       ██     ███     ██      █
XAUUSD H1       ███        ███        ███       █        █       ██     █       ░       ██
```

This matrix tells you exactly which instrument/TF combination feeds which sparse regime. No guessing.

### 2B. Cross-instrument calibration transfer
**Method:** For each sparse regime, calibrate on the instrument/TF where it has the most samples. Apply a **transfer discount** (e.g. 0.6× weight) to account for cross-instrument IC uncertainty. The transferred parameters start at reduced confidence and must earn full confidence through live observation on the target instrument.
**Mathematical basis:** The regime dynamics (trend structure, mean-reversion, momentum) are universal market microstructure properties. The specific magnitudes differ across instruments but the *relative* signal rankings are more stable. Transfer the rankings with a confidence discount, not the raw parameter values.
**Output:** Per-regime transfer viability score and initial parameter seeds for the 5 sparse regimes.

### 2C. Parallel demo across instruments
**Method:** Run TUNGSTEN on 3–4 instruments simultaneously on demo. This multiplies trade frequency by the number of instruments. At 3 trades/day/instrument across 4 instruments = 12 trades/day total. The 100-trade minimum for statistical confidence is reached in ~8 days instead of ~5 weeks.
**Output:** Per-instrument, per-regime trade log feeding 1D above.

## 3. EXECUTION PROOF — confirm the mechanics in days, not weeks

*Demo doesn't prove edge. Demo proves the code runs. Prove it fast and move on.*

### 3A. Mechanical stress test (2–3 days)
Run on demo and verify:
- Orders send with correct lot, SL, TP — no rejection, no missing stop
- Spread gate blocks during spread spikes (simulate by running during high-impact news)
- Reconnect recovery: kill the terminal, restart, verify state loads and open positions retain their stops
- Weekend gap: leave running over a weekend, verify Monday open doesn't trigger false signals or crash
- Calibration runs to completion without timeout, produces sensible per-regime parameters
- TLog appends correctly, structured decision log captures every entry/skip with reason
- Self-regulation: artificially degrade conditions (if possible on demo) and verify drift detection → quarantine

### 3B. Execution quality baseline
Record from the first 20–30 demo trades:
- Slippage distribution (requested vs filled price)
- Fill time distribution
- Spread at entry vs spread ceiling
- Rejected order rate and reasons

This is the execution cost model. It feeds back into edge estimation: if slippage + spread consistently eat X% of the expected R, the edge estimate must be discounted by X%.

## 4. MATHEMATICAL EDGE QUANTIFICATION — the numbers that matter

*Not "it looks good." Numbers, with confidence intervals.*

### 4A. Per-regime edge profile
For each regime that calibration armed (currently 3, potentially all 9 after §2):

| Metric | How computed | Minimum for GO |
|---|---|---|
| Win rate | OOS ghost + confirmed live | ≥ floor (regime-specific, currently 65%) |
| Profit factor | sum(wins) / sum(losses) | > 1.3 |
| Expectancy per trade | (WR × avgWin) - ((1-WR) × avgLoss) | > 0.15 R |
| Sharpe (annualised) | mean(R) / std(R) × √(252×trades/day) | > 1.0 |
| Max drawdown | worst peak-to-trough in OOS | < daily loss halt threshold |
| Edge half-life | from §1C | > recalibration frequency |
| Sample size | OOS trades in this regime | ≥ 100 |

Any regime below the minimums stays `UNQUALIFIED` regardless of code quality.

### 4B. Portfolio-level aggregation
When multiple regimes are armed, compute the portfolio-level metrics — accounting for regime correlation (do drawdowns overlap?). The portfolio Sharpe should exceed the best single-regime Sharpe if regimes are genuinely orthogonal. If it doesn't, the regimes are correlated and the diversification is illusory.

### 4C. Confidence intervals on everything
No point estimate without a confidence interval. WR of 68% means nothing without "68% ± 4% at 95% CI based on N=150 trades." If the lower bound of the CI dips below the profitability floor, the evidence is insufficient — you need more trades, not more optimism.

## 5. LIVE RAMP PROTOCOL — the fastest honest path from demo to real money

### 5A. Demo gate (days 1–5)
- §3A mechanical stress test passes
- §3B execution quality baseline established
- Calibration runs clean (§1A, §1B)
- At least one regime has edge profile (§4A) above all minimums

**Exit criterion:** no mechanical failures, calibration trustworthy, at least one armed regime. Move to micro.

### 5B. Micro-live gate (days 6–20)
- Minimum lot size on real account
- §1D ghost-vs-live reconciliation running continuously
- Track: does realised WR/PF match calibration's prediction within tolerance?
- CEO tier system active: starts in Building tier, earns Proven through live results
- Self-regulation layer active: drift detection, quarantine, daily loss halt all armed

**Exit criterion:** 50+ live trades, realised metrics within 1 standard deviation of predicted, no kill-switch trips, no quarantine events. Scale up.

### 5C. Scale protocol (day 20+)
- Increase lot size by fixed increments (e.g. 2×) at each confidence gate
- Each gate requires another 30+ trades at the new size with metrics holding
- The CEO tier system governs this naturally — competence score rises, risk ceiling expands, concurrent trades increase
- Any kill-switch trip or quarantine event freezes scaling and triggers review

**Total timeline: 3–4 weeks from Sword completion to meaningful live trading.** Not months. The math works because calibration already did the heavy testing, demo proves mechanics in days, and micro-live IS the edge test — you're not waiting to test, you're testing by trading at a size where being wrong costs almost nothing.
